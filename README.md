# playwright-todo-tests
 
Учебные UI-тесты на Playwright (JavaScript) для демо-приложения
[TodoMVC](https://demo.playwright.dev/todomvc) — списка дел, который команда Playwright
сделала специально для тренировки автотестов.
 
Цель проекта — разобраться с UI-автоматизацией: локаторами, автоматическим ожиданием,
параметризацией тестов и тем, как сделать так, чтобы тест действительно что-то проверял.
 
## Запуск
 
Нужен Node.js 18 или новее.
 
```bash
npm install
npx playwright install chromium
npx playwright test
```
 
Тесты запускаются только в Chromium — остальные браузеры в `playwright.config.js` отключены.
 
Отчёт после прогона:
 
```bash
npx playwright show-report
```
 
## Что покрыто
 
**Добавление дел**
 
- одно дело появляется в списке;
- два дела появляются в том порядке, в котором добавлены.
**Текстовый ввод** — табличный тест, каждый случай отдельным тестом:
 
| Случай | Ввод | Ожидаемый текст |
|---|---|---|
| обычный текст | `Купить молоко` | `Купить молоко` |
| пробел в начале | ` Купить молоко` | `Купить молоко` |
| пробел в конце | `Купить молоко ` | `Купить молоко` |
| пробелы внутри сохраняются | `Купить    молоко` | `Купить    молоко` |
| эмодзи | `😀` | `😀` |
| символы | `%$` | `%$` |
| HTML как текст | `<b>жирный</b>` | `<b>жирный</b>` |
 
Последний случай проверяет, что ввод пользователя отображается как текст, а не вставляется
в страницу как разметка. Иначе это была бы уязвимость XSS.
 
**Пустой ввод** — пустая строка и одни пробелы не создают дело. После пустой попытки тест
добавляет обычное дело и проверяет, что в списке ровно оно: так видно, что пустое дело
не появилось, а поле ввода осталось рабочим.
 
**Побочные эффекты добавления**
 
- поле ввода очищается после добавления;
- счётчик показывает `1 item left`, затем `2 items left` — проверяется граница
  единственного и множественного числа.
**Отметка выполненным**
 
- отмеченное дело получает класс `completed`, счётчик уменьшается;
- снятие отметки возвращает дело и счётчик в исходное состояние.
**Удаление** — кнопка удаления появляется при наведении на строку. После удаления
проверяются счётчик и то, что остались именно другие дела, в прежнем порядке.
 
**Фильтры** — Active, Completed и All показывают нужные дела, адрес страницы меняется
на `#/active`, `#/completed` и `#/`.
 
**Редактирование** — двойной щелчок по тексту дела открывает поле редактирования.
Табличный тест: в каждом случае первое из двух дел переводится в режим редактирования,
проверяется, что в поле стоит старый текст, затем вводится новый и выполняется выход.
 
| Случай | Ввод | Выход | Результат |
|---|---|---|---|
| Enter сохраняет | `Мясо` | Enter | `Мясо`, `Овощи` |
| Esc отменяет | `Мясо` | Escape | `Молоко`, `Овощи` |
| щелчок мимо сохраняет | `Мясо` | щелчок по заголовку | `Мясо`, `Овощи` |
| пустой текст удаляет дело | пустая строка | Enter | `Овощи` |
 
Способ выхода хранится в строке таблицы как функция, поэтому в теле теста нет условий:
тест вызывает функцию текущего случая. После выхода проверяется, что на странице не
осталось строк в режиме редактирования, и итоговый список дел — он заодно показывает,
что соседнее дело не изменилось.
 
Ожидаемое поведение сначала выяснено вручную и сверено со спецификацией TodoMVC.
 
## Что выяснилось по ходу
 
**`toHaveText` нормализует пробелы.** Сравнение со строкой обрезает пробелы по краям
и схлопывает повторы внутри — и в ожидаемом, и в полученном тексте. Тесты на пробелы с такой
проверкой проходили бы, даже если бы приложение ничего не обрезало. Поэтому текстовые случаи
сравниваются точно, через `textContent()`.
 
**Пробелы внутри текста приложение сохраняет.** Точная проверка показала, что
`Купить    молоко` хранится как есть, хотя браузер показывает один пробел. Это соответствует
спецификации TodoMVC: обрезать нужно только края. Тест фиксирует это поведение.
 
**Найденный элемент ещё не значит, что по нему можно щёлкнуть.** Первая версия теста
щёлкала по счётчику дел, и Playwright отказывался: поверх счётчика лежит список фильтров
(`<ul class="filters"> intercepts pointer events`). Перед щелчком Playwright проверяет,
что в точке щелчка окажется именно нужный элемент, — пользователь там попал бы
по фильтрам. Обходить проверку через `force: true` не стал, щелчок перенесён на заголовок.
 
**Локатор — это описание поиска, а не снимок элемента.** `todos.nth(0)` после удаления
первого дела указывает уже на следующее. Проверка «у первой строки нет класса `editing`»
в случае удаления смотрела бы на дело, которое не редактировалось, и проходила бы всегда.
Поэтому проверяется, что режим редактирования не открыт ни у одной строки.
